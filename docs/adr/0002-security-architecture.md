# ADR 0002: Security architecture for sensitive deal documents

Status: proposed, 2026-10-25. Not built. Written for a later run; nothing here changes the code until its cards exist.
Supersedes nothing. ADR 0001 (local stack) put virus scanning out of scope; section 4 reverses that on a stated basis.

## 1. What is protected, and from whom

A deal package is close to the most sensitive thing a small developer owns: purchase agreements, bank term sheets,
personal financial statements and guarantees, sometimes government identifiers. Four adversaries, in order of
likelihood:

| Adversary | What they would do | What stops them |
|---|---|---|
| A stranger on the internet | Guess a share link or a password; upload a malicious file to run code in the worker | Hashed tokens and rate limits (exist); MFA (§6); the worker jail (§4) |
| Another customer | Reach a deal in another workspace through a query bug | Row-level security in the database (exists); per-workspace keys, so a query bug alone yields ciphertext (§3) |
| Agir, or whoever holds Agir's access | A stolen laptop, a leaked `DATABASE_URL`, a compromised host | Envelope encryption with keys in a KMS; no standing production access; key-use audit (§3, §6) |
| A deletion request | A customer, a lawyer or a regulator wants a deal gone, including from backups | Crypto-shredding: destroy the workspace key (§3.4) |

One limit is stated up front. **Agir cannot be end-to-end encrypted.** The server must read the documents to find
figures, render reports and send text to the model. The goal is therefore not "Agir never sees the data" but:
*nothing but the live worker, for the seconds it works on one deal, ever holds plaintext, and every such moment is
attributable.*

## 2. Principles

1. **The database is the one place access is decided.** Row-level security, `agir_is_member`, `agir_is_staff` and
   the security-definer functions already do this. No second authorization layer in the API that can drift.
2. **Encryption keys are per workspace and never stored next to the data.** A copy of the disk, the database or a
   backup is useless without the KMS.
3. **Plaintext lives only in worker memory, per job.** Not on disk, not in logs, not in a long-lived column.
4. **Everything that leaves the Canadian boundary is named, minimised and switchable.** Today that is one thing:
   addressed document text sent to Anthropic.
5. **Deletion is a key operation, not a row operation.** Then backups cannot contradict the privacy notice.
6. **Every access to a document is an audit event with an actor.** The hash chain exists; it needs the actor hashed
   in, and one chain per workspace.

## 3. Encryption

### 3.1 In transit

TLS at the edge with HSTS. A private network, or mutual TLS, between the API, the worker and Postgres. The database
connection uses `sslmode=verify-full`. Today the server binds `127.0.0.1` and assumes a proxy; nothing else exists.

### 3.2 At rest: two layers

- **Volume encryption** from the hosting provider. Baseline only: it protects a lost disk, not a leaked credential.
  Turn it on and do not count it.
- **Envelope encryption in the application**, the layer that matters:
  - A **KMS master key** in a Canadian region (AWS KMS `ca-central-1`, Google Cloud KMS
    `northamerica-northeast1`, or Azure Key Vault Canada Central). It never leaves the KMS.
  - A **data encryption key per workspace** (DEK), generated by the KMS and stored wrapped in a `workspace_keys`
    table with its version.
  - Each **blob** encrypted with AES-256-GCM under the workspace DEK, a fresh 96-bit nonce, and the storage key plus
    the workspace id as associated data, so a blob cannot be moved between workspaces. The nonce, key version and
    authentication tag are stored with the ciphertext.
  - This is a wrapper around the existing `BlobStore` (`packages/db/src/storage.ts`): `encryptingStore(inner,
    keyring)`. The interface does not change; `put` still returns `{ key, sha256, size }`.
  - One change to content addressing: today a blob's key is its SHA-256 and identical files are stored once across
    all workspaces. With per-workspace keys that cannot hold, and it should not anyway (it tells one customer whether
    another holds the same file). The key becomes `workspace/sha256`.

### 3.3 In the database

Postgres rows carry document text, not only the blobs: `ai_readings.request` (the full text sent to the model),
`ai_readings.response`, `candidates.raw` and `candidates.context` (quoted lines), document names, deal names.

- **Encrypt the text columns the same way**, application-side under the workspace DEK, so a database administrator
  or a dump sees ciphertext. Columns the engine queries (ids, statuses, numbers, hashes) stay in clear; row-level
  security covers them.
- **Stop storing `ai_readings.request`.** It exists for replay, and replay is deterministic:
  `addressedText(documents)` at `documents_hash` with `prompt_version` reproduces the request exactly from the
  stored documents. Keep the hash and regenerate on replay. This removes the largest plaintext copy in the system.

### 3.4 Keys and deletion

- **Rotation.** The KMS master key yearly (the KMS re-wraps the DEKs; blobs are not rewritten). A workspace DEK on
  demand: the worker re-encrypts that workspace's blobs, a bounded job.
- **Crypto-shredding.** Deleting a workspace, or expiring a deal's documents past retention, destroys the DEK
  version. Every copy, including every backup, becomes unreadable at once. The question "what does deletion mean for
  backups" becomes a documented, testable procedure.
- **Run signatures.** `AGIR_RUN_SIGNING_SECRET` is an HMAC secret in an environment variable. Move it to an
  **asymmetric KMS key**: the private key never leaves the KMS, and a lender holding a report can verify the
  signature with the public key. That makes the "signed run" promise literal.
- **Backups** encrypted under a separate backup key, kept in Canada, with a quarterly restore drill (plan step L2).

## 4. The processing boundary: the worker

The worker is where untrusted bytes meet parsers (pdfjs, exceljs, mammoth, tesseract, Chromium). It is the most
likely place for code execution and must be the most locked-down process Agir runs.

- Its own container: non-root, read-only root filesystem, `tmpfs` scratch wiped per job, memory and CPU limits
  (the memory cliff is already known), the default seccomp and AppArmor profiles.
- **No inbound network.** Egress allow-list: Postgres, the blob store, the KMS, `api.anthropic.com`. Nothing else, so
  a compromised parser cannot exfiltrate anywhere Agir does not already send data.
- Decrypt in memory only, one deal at a time; never write plaintext to disk. OCR uses `mkdtemp` for language data
  only; keep it so.
- Chromium for PDFs runs in the same jail with its sandbox on.
- The zip-bomb and page caps exist (card 47b). Add **ClamAV** to the worker image: it is cheap, it answers plan step
  L4's EICAR test, and it reverses ADR 0001's "out of scope" on a stated basis.

## 5. The model boundary

The only data that leaves Canada.

- A zero-data-retention agreement with Anthropic (the owner's card 162 decision of 2026-10-24); the inference region
  pinned to `us` in code; both recorded in the privacy notice.
- A **per-workspace "read documents without AI" switch**, chosen at sign-up and visible on every deal.
- Minimise: addressed text is sent, never files. Add a redaction pass for patterns that are never figures (social
  insurance numbers, phone numbers, email addresses, account numbers) before the text leaves; the verifier does not
  need them.
- Store nothing of the request (§3.3); store the response encrypted; expire it with the deal.

## 6. Identity, sessions and sharing

- **MFA for every staff role**, mandatory for owners and admins: TOTP now, passkeys as the preferred path. Clients on
  share links need no account.
- Sessions: tokens are random and stored hashed; the device list exists (migration 0034). Add an absolute expiry on
  top of the 14-day sliding one, and invalidate every session on a password or email change.
- Share links: hashed tokens with expiry exist. Add an optional passcode the sender gives the lender by another
  channel, a per-link open count with a cap, and a visible watermark ("Prepared for X, shared with Y on <date>") on
  PDFs opened through a link.
- No standing production access for Agir staff. Support access uses the mechanism the review-access screen already
  has: a time-boxed grant by the owner, with an audit event at grant and at expiry. Operational break-glass is a
  separate, alarmed path.

## 7. Audit and operations

- Fix the two known gaps: one chain per workspace, the actor inside each event's hash, and
  `GET /api/workspaces/:ws/audit/verify` scoped to the caller's workspace.
- Revoke `update` and `delete` on the audit table from the application role at the grant level, not by convention.
- Ship logs off the host; log event names and ids, never content (the API already redacts shared-link errors; make
  that the rule everywhere).
- Alerts: failed-login bursts, share-link guessing, one account downloading many deals, anomalies in KMS decrypt
  calls.
- CI: dependency vulnerability scan, pinned lockfile, secret scanning, a signed release record (L1). An external
  penetration test before the pilot (L4; the owner books it).

## 8. The cards

Nothing here except the provider choice waits on a person.

| Card | Scope | Size |
|---|---|---|
| S1 Envelope encryption | `workspace_keys` migration, KMS client, `encryptingStore`, workspace-scoped blob keys, migration of existing blobs | 3–4 days |
| S2 Sensitive columns | Encrypt the text columns; drop `ai_readings.request` and regenerate on replay | 2 days |
| S3 Worker jail | Container spec, egress policy, tmpfs, ClamAV, Chromium sandbox | 2 days, with the deployment recipe |
| S4 KMS-signed runs | Asymmetric signing; public verification in the audit package | 1–2 days |
| S5 Crypto-shred deletion | Delete a workspace or expire a deal's documents by key destruction; a dry-run report first | 2 days; the retention period is the lawyer's |
| S6 MFA and sessions | TOTP and passkeys, absolute expiry, invalidation on credential change | 3 days |
| S7 Model boundary | Region pin, per-workspace switch, redaction pass | 2 days |
| S8 Audit and operations | Per-workspace chain with actor, scoped verify, grants, alerts | 2 days; the migration needs owner review |

About three weeks. S1 to S3 come before any real document is uploaded. S1 and S4 need the KMS, which means the
hosting provider.

## 9. Decisions for the owner

1. The hosting and KMS provider; this fixes the Canadian region for keys, database, blobs, backups and logs.
2. Whether MFA is mandatory for all staff or only for owners and admins.
3. The retention period after a deal closes, and whether a customer can choose a shorter one.
4. Whether Agir staff ever get support access to a workspace, and under what grant.
5. Whether to drop `ai_readings.request` (recommended) or keep it encrypted.

## 10. What this deliberately does not do

- Client-side end-to-end encryption: it would make reading, review and reports impossible.
- Home-made cryptography: AES-256-GCM through Node's `crypto`, keys from a KMS, nothing else.
- Rely on disk encryption alone, or on the application to decide access instead of the database.
